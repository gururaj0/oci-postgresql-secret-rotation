# Controlled recovery

Never assume that switching a Vault version changes PostgreSQL's password. Prefer rolling forward the recorded pending credential after proving it authenticates.

1. Identify tenancy/region/DB/role and record the operation UUID/state/version references from `status`. Disable the Vault schedule with `unschedule --confirm`. Prevent manual rotations and stop any other invocation source. Restrict incident notes to identifiers; never paste secret contents.
2. If the role is locked, determine whether the prior Function or local process is still alive. Stop it and wait for its configured execution timeout and any in-flight database request to finish. Review OCI invocation/audit logs. A lock has no automatic expiration because elapsed time alone cannot prove the old actor stopped.
3. Run `reconcile --confirm`. Only if an abandoned lock remains **and you have confirmed the previous invocation is stopped**, add `--previous-invocation-stopped`. This conditionally removes that exact lock, reacquires exclusivity and reads the journal. Never use the flag on a live invocation.
4. At PRECHECK the engine finds an existing version by the operation's unique name or creates it once. At PREPARED it tests the pending password first; if it works, no second password update is needed. If only the recorded old password works, it applies the same pending password. At DATABASE_UPDATED it verifies the pending credential, then promotes it under the expected Vault ETag/current version. VERIFIED retries promotion without generating another credential. VAULT_PROMOTED verifies CURRENT and a fresh database login before completing.
5. Connectivity/TLS errors stop reconciliation because they do not prove a password is wrong. If neither credential authenticates, or an external operator changed Vault CURRENT, stop and escalate to the approved DBA/Vault owners. Use their separate credential-reset procedure; preserve both version references and journal evidence. Do not improvise SQL for the OCI-managed administrator.
6. Validate the application's refresh and a new physical connection using CURRENT. Review alarm recovery and the operation completion timestamp. Obtain approval to resume the rotation schedule.

If application authentication fails after a completed rotation, first force a secure secret refresh and connection-factory update. If database state needs correction, use the approved DBA procedure to apply a selected retained credential **to PostgreSQL**, verify it, then promote that same Vault version. This exceptional rollback must be recorded and explicitly approved. Do not simply promote PREVIOUS.

Uninstall is staged: disable the Vault schedule, deactivate the monitor schedule through reviewed Terraform, reconcile all incomplete operations, then review `uninstall --plan`. Journal bucket and optional new Vault/key have `prevent_destroy` safeguards. Preserve working credentials and recovery evidence; any destructive removal requires a separate approved Terraform change. `uninstall.sh` only plans removal.
