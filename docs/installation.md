# Installation and approval sequence

Start with [choosing your deployment host](../DEPLOYMENT.md#choose-your-deployment-host) and the [task/location table](../DEPLOYMENT.md#tasks-and-where-to-run-them). An OCI Compute VM with private database access is recommended; a laptop with VPN or an SSH tunnel is also supported. Run installation and Terraform on that host. Download the database CA using the [certificate instructions](../DEPLOYMENT.md#obtain-the-postgresql-ca-certificate); no certificate or private-key generation is required.

1. Use an OCI-authenticated customer host with Python 3.11+ and private database connectivity. Confirm the intended default profile locally; do not copy its keys into this repository or into Functions. Run `install.sh`, then activate `.venv`. For restricted environments, install the release's resolved hash lock from an approved wheel mirror.
2. Run `discover`. It enumerates subscribed regions rather than assuming the profile region contains the DB. Partial results carry errors; an empty list with an error is not proof that a resource is absent. Run `configure` and select the region, existing database, Vault/source secret and private subnet. Discovery and configuration make no cloud changes. If no Vault exists, review/apply the optional `modules/vault` bootstrap separately with a tenancy administrator, then rerun discovery.
3. Select a login application role. The initial Vault value must be UTF-8 JSON with exactly `username` and `password`. Use an existing matching secret, or set `secret_id: UNINITIALIZED` in a local configuration and run `create-secret --key-id KEY_OCID --name NAME --confirm`. This identifies the target, securely prompts for the existing database password, checks authentication, and creates the secret through the SDK. Set the returned OCID in configuration. No password is written to a local file or Terraform.
4. Set the CA path and TLS hostname. For local validation the CA file must exist locally; the image must contain the same trusted bundle at its configured runtime path. Build from the package root: `docker build -f functions/vault_rotation/Dockerfile -t YOUR_OCIR_IMAGE .`. Add a Dockerfile `COPY` for the non-secret CA bundle under `/function/certs/` and make it readable by UID 10001. Push using customer-managed OCIR authentication and record the immutable `@sha256:...` image URI in configuration. Use a compatible image architecture for the selected Functions application.
5. Run `validate` from the private network and review IAM with the administrator. Read-only validation proves the operator's read access and database TLS/login; it cannot prove the not-yet-deployed Function's network and write privileges. Review the proposed private subnet, routes, DNS, NSGs and service gateway/NAT access to Vault, Secrets, Object Storage, Monitoring and OCIR.
6. Run `plan`. It writes identifiers/settings to `terraform/rotation.auto.tfvars.json`, initializes providers, and prints a concrete Terraform plan. For an existing journal bucket set `create_state_bucket=false` in a separate `.tfvars` file or import only that bucket. Back up Terraform state in customer-owned encrypted storage. Never import credential content.
7. Obtain explicit approval of tenancy, region, DB, role, IAM, resource creation and cost. Run `deploy --confirm`; Terraform displays its plan and requires its normal interactive approval. It creates the Function, journal bucket if requested, policies, logs, optional alarms and the read-only monitoring schedule. The credential rotation schedule remains off.
8. Set `function_id` from Terraform output. Invoke with `{"action":"validate"}` using the OCI Console or SDK to confirm resource-principal access and private DB connectivity. Check the monitor heartbeat and notification delivery. Run a manually approved application-role rotation in the acceptance environment and follow the customer handoff tests.
9. Enable rotation only after acceptance with `schedule --confirm`. This invokes Function validation first, then attaches the supported Function target and interval to the existing secret. Verify the resulting schedule with `status`. Disable through `unschedule --confirm` before teardown or maintenance.

`requirements.resolved.lock` contains the tested transitive dependencies and hashes; the installer and Dockerfile use it. `requirements.lock` records direct pins. The delivery also includes the validated Terraform provider lock. Regenerate and review both locks when updating dependencies, rerun `scripts/release-check.sh`, and scan the built image before deployment.
